# V06 查核報告：故障注入未持續成立

查核時間：2026-11-27T04:47:48+08:00（Asia/Taipei）。本次只查核，不修改遊戲、既有測試、guard 或驗收標準，不開功能 PR、不合併、不部署、不升版。

已找到可重現的失敗機制：V06 以每 20 毫秒一次、僅在 `G.phase==='node'` 時寫入 `busy=true` 的計時器模擬「一直忙」。遊戲流程會正常清除忙碌狀態；V06 沒有就緒確認，這個計時器也無法保證持續忙碌。等待器在兩個空閒窗口正常通過後，六步只剩四次逾時，因未達「至少五次」而使自我驗收失敗。

這是重現資料確認的測試情境問題；不代表遊戲發生錯誤，也不是等待器把這四次逾時吞掉。

## 逐步證據與失敗機制

以當時版本第 11 輪的 1280×720 為例：

| 步驟（從零起算） | 狀態／操作 | 等待毫秒 | 逾時 |
|---|---|---:|---|
| 0 | A1：摸黑走到門邊 | 256 | 否 |
| 1 | A1d：看門背後的逃生路線圖 | 256 | 否 |
| 2 | AO2：開門讓他進來 | 801 | 是 |
| 3 | AO2：已在戰鬥，沒有可點的選項 | 799 | 是 |
| 4 | AO2：戰鬥演出中 | 801 | 是 |
| 5 | AO2：關骰子 | 801 | 是 |

六步合計四次逾時，exit=1、三份 trace 都存在，但原 V06 要求每個尺寸至少五次，因此整體判失敗。第 13 輪也走出相同路線，前兩次等待為 255、257 毫秒。

觀察組四個失敗輪同樣走出這條路線。第 4 輪兩次條件成立的當下，直接記錄到：

```json
[
  {"at":2900.7,"busy":false,"gbusy":false,"phase":"node","node":"A1d","fight":false,"over":false,"queue":0},
  {"at":3316.3,"busy":false,"gbusy":false,"phase":"node","node":"AO2","fight":false,"over":false,"queue":0}
]
```

其餘三個失敗觀察輪也在相同兩個節點記錄到兩個忙碌旗標皆為 false、over=false。上面的時刻為方便閱讀的四捨五入值；完整原值與六步 trace 見證據 JSON。

程式與資料可連成以下流程：

1. V06 的計時器每 20 毫秒只在 node 階段寫入 busy=true，沒有先確認故障已啟用。
2. 真實選項流程會切到 busy 階段，完成時 `run()` 的 finally 正常寫回 busy=false、G.busy=0。
3. 在下一次注入計時器之前，真實 Playwright 等待條件讀到兩個 false，因此正確結束等待；上述兩次空閒窗口已直接觀察到。
4. 操作得以繼續，最後進入 fight 階段，原注入的 node 條件也不再涵蓋；剩下的逾時混入真正的戰鬥忙碌，已不是可靠的「一直忙」控制情境。
5. 自我驗收用固定的五次門檻檢查這個不持續的故障，結果便會隨時序改變。

這些證據支持修正故障注入的持續性與啟用時機。單純增加 800 毫秒等待無法保證故障成立，還可能讓正常遊戲更容易在期限內完成；不應降低五次門檻或把重跑通過當修復。

## 原始失敗紀錄的限制

原失敗工作流程 `45856556564` 首輪、job `140036348247`、artifact `15137791844`，只留下 V06 的摘要：exit 1、判定 false、三份紀錄、第一個尺寸逾時六次。

該 artifact 的 browser-smoke.json 實際是正常四十步冒煙測試，種子為 1800402593／1800402594／1800402595；並不是 V06 的六步、種子 1／2／3。原自我驗收用 mktemp 建立故障複本，結束時 trap 刪除，卻沒有先把 V06 的 out 複製進 test-results，所以不能逐步還原原始那一輪，更不能斷言原始那次一定也是 1280×720。

上次「紀錄已保留」的說法不夠精確：保留了失敗摘要，沒有保留 V06 本身的完整故障證據。本報告將歷史那次的不可還原限制，與這次相同版本的可重現機制分開敘述。
