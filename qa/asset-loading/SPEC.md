## 0. 給接手的 GPT／Claude／Codex

請以最新 main 為起點，依本文件落實 B 方案：分級預載、跨頁本機快取、自動重試、合理備援、演出同步及低速網路驗收。目的不是單純增加載入畫面，而是消除可避免的音效漏播、晚播、立繪與特效延遲或缺失。

## 1. 現況與可確認的問題

玩家回報：有時音效、圖片未及時載入，導致延遲出現或完全沒有出現。已讀取基準版 index.html 完整原始碼、版本紀錄及 `tests/browser-audio.cjs`、`docs/QA_SYSTEM.md`。下列是程式證據，並非 Android 實機重現結論。

| 位置（基準版約略行號） | 現行行為 | 風險 |
|---|---|---|

既有真實瀏覽器音訊測試會使用允許自動播放的 Chromium，點擊入口後主動 `await loadSounds(); await loadArrowSound();`，再量波形。因此正常環境通過不能證明冷快取、低速網路或素材未就緒時也能正常演出。

## 3. 實作架構

### 3.1 共用素材管理層

建立單一素材登錄表及載入管理器（命名僅為建議：`ZC_ASSETS`／`ZC_ASSET_LOADER`，新增前先搜尋全域衝突）。以實際資料表、SFILES、FOE_IMG、武器與 VFX 路徑、BGM_MIX、字型、主選單／角色／場景圖片及現有動態路徑產出清單。不可只搜尋寫死的 HTML 路徑。

每筆素材應有唯一 ID、相對 URL、型別、優先等級、版本內容雜湊、必要性、格式備選、狀態、嘗試次數、失敗原因、最後使用時間。圖片與音效需區分「下載完成」與「解碼／可播放完成」。建議統一狀態：idle → queued → fetching → decoding → ready；失敗則 failed／retrying；有備援時 degraded，不能把 degraded 偽裝成 ready。

同一檔案的併發請求共用進行中的 Promise；成功後重用；失敗後清除失敗 Promise，允許重試。音訊、圖片的現有載入函式可保留為相容包裝，避免破壞呼叫端與既有 QA 介面，如 `loadSounds()`、`soundStatus()`、`BUF`、`loadArrowSound()`。

### 3.2 分級排程

| 優先 | 素材 | 啟動時機 |
|---|---|---|
| P0 入口 | 核心 HTML／JS、既有字型、開場必要圖片、選單必要素材 | 開啟網頁，最早載入 |
| P1 開局必要 | 選用角色與必要 UI、開場劇情圖片、常用互動／受傷／戰鬥音效、可能立即使用的既有立繪與基礎特效、探索配樂可播放資料 | 入口及選角期間；進入遊戲前確認必要項目就緒或適當備援 |
| P2 近期戰鬥／場景 | 其他武器聲、敵人立繪、對應 VFX、一般／激戰配樂可播放資料、目前地區相關素材 | 選角、開局、探索空檔預載，使用前提高優先權 |
| P3 低頻資源 | 遠期地區、低頻事件音效與不影響近期遊玩的素材 | 背景分批載入；可取消／降低優先權 |

優先分類須依最新遊戲實際路線校正。不可因為 P2／P3 的分類讓任何必然會在 P1 演出使用的資源漏載。預載可依區域候選集或武器類別，不得偷跑亂數、提前生成實際遭遇或改動遊戲資料。

建議初始參數（工程預設，非主人定案的遊戲規則）：下載同時 3～4 筆，音訊解碼 1～2 筆，低記憶體或低速裝置降低併發；短檔請求逾時 10～15 秒，首次失敗後最多再重試 2 次（含首次共 3 次），約 0.5／1.5 秒退避並加少量非遊戲亂數抖動。大型素材依實測另訂合理逾時。不以固定值硬套所有裝置；調整後報告實際設定與理由。必要檔案可插隊，背景請求不可阻塞入口。

### 3.3 入口與行動瀏覽器音訊解鎖

1. 網頁載入後即開始下載必要的公開素材；可與原開場動畫平行進行，但不因動畫未完成而阻塞開發。
2. 保留玩家明確點擊「進入遊戲」的操作。在同一次真實使用者手勢中建立／恢復 AudioContext、嘗試啟動允許的配樂，避免把音訊解鎖放到長時間 await 之後。尊重使用者音效／配樂設定。
3. 點擊後若必要素材尚未就緒，保持簡潔初始化畫面；達到就緒條件才進入原本的流程（選單可先顯示，但不可進入需要尚未就緒的演出）。選單與開局之間可再設必要資源檢查點，不必等待全素材完成。
4. 進度顯示以真實必要任務數或可驗證位元組為準；「下載完成」與「音訊準備完成」可分開。建議用「正在初始化資源」「正在準備音效」「正在載入圖像」等中性文字，不顯示劇情名稱或內部技術資訊。進度百分比屬載入介面、非遊戲核心數值；若主人不希望看到百分比，改成不帶數字的真實進度條即可。
5. 短檔反覆失敗時停止無限等待。建議一次前景載入有 20～30 秒上限（實測調整）；提供「重新載入資源」及在安全備援存在時「繼續遊戲」兩個操作。必要核心失敗不得假裝成功；清楚說明網路或資源異常，允許再試。音效關閉時不應因音效解碼而阻止開局；之後開啟時重新準備。
6. AudioContext 為 suspended／interrupted 時嘗試恢復並檢查結果；若瀏覽器仍拒絕播放，提示玩家再點擊以啟用音訊。音訊就緒與音訊已解鎖分開紀錄，不以背景下載取代使用者手勢。

### 3.4 快取：Service Worker + Cache Storage

GitHub Pages 已使用 HTTPS，可採標準 Service Worker。建議新增根目錄 `sw.js` 及由工作環境生成的版本化素材索引（例如 `assets-manifest.json`；不使用已移除的舊 MANIFEST.json 名稱，除非最新流程已有明確規定）。若有現行快取機制，先整合再決定是否需要新增。

- 註冊與 scope 以 `/zerocase/` 為界；路徑使用相對於部署根目錄的 URL，不能誤寫成網域根目錄 `/sfx/`。僅攔截同源、遊戲 scope 內、明確列入清單的 GET 靜態資源。
- HTML／版本索引／SW 更新檢查使用 network-first 或等效新鮮度策略，不能讓玩家長期卡在舊 index.html。已知內容雜湊的靜態資源使用 cache-first。內容變更才更新快取鍵，未變更素材跨版本重用，不整包重下載。
- 素材索引生成需在發布流程中維持一致性。使用內容雜湊查詢參數或等效可驗證鍵；不要用每次開啟的時間戳當版本。首次頁面尚未受 SW 控制時，下載管理器仍需有效；不得假設註冊立即等於受控。新舊索引與素材版本需相容；可檢查內容雜湊防止部署過渡期把錯誤內容存入新版本快取。
- 成功的完整回應才進快取；不快取 404／500、錯誤頁、被取消請求或不完整資料。對 `Range` 媒體請求採可正確回應 206 的完整檔切片方案，或明確繞過，禁止回傳錯誤的 200／206。長配樂以串流／瀏覽器媒體快取為主，不要求每次解碼或下載整首才開局；若需完整離線配樂，另實測成本後決定。
- 不攔截 Firebase、登入／房間狀態、個人頭像上傳、存檔或其他外部 API；不將私人資料存入 Cache Storage。跨版本清除僅限本遊戲所管理的過期快取，不刪除 localStorage、IndexedDB 存檔或其他網頁的快取。
- 不使用無條件 skipWaiting/clients.claim 強制進行中的遊戲切換版本。新版本提示與生效應在主選單／安全時點，避免多人局中混用新舊資源。舊版仍被分頁使用時保留必要資源；安全後清理。
- 快取儲存可能因瀏覽器配額、清理資料或無痕模式被移除，不能宣稱永久保存。SW 不支援／註冊失敗／配額不足時，回退一般 HTTP 載入及記憶體重用，遊戲仍可運作；不得因快取功能失敗就卡死。
- 可提供診斷用「重新下載遊戲素材」功能，僅清除素材快取；不得將玩家存檔、角色解鎖或設定一併清除。完整離線遊戲、PWA 安裝與離線多人不在本次範圍。

### 3.5 記憶體與效能

磁碟快取保存壓縮資源；記憶體僅保留近期常用的已解碼 AudioBuffer／圖片。短音效解碼後記憶體量可用 length × channels × 4 bytes 估算，圖片依實際解碼尺寸估算；不能只看下載大小。以 Android 低／中階裝置為目標，先測素材總容量，再訂記憶體預算（建議起始音效解碼快取 32～64 MiB、圖片依實測調整，不是必須上限）。近期／正在演出的資源固定保留；低頻項目依最近使用時間釋放，可從磁碟重新解碼。避免解碼大批圖片造成主執行緒卡頓或 QTE 掉幀。不得為省空間自行降低立繪品質、重新壓縮主人指定的音效或裁切圖像。

### 3.6 失敗重試、備援與正確播放時機

- 下載／解碼失敗時記錄資源 ID、階段、錯誤、時間、重試次數，網路恢復後重排失敗清單（注意 `online` 事件不等於真的可連線）。同一資源達上限後需冷卻，避免連續戰鬥觸發重試風暴。
- 圖片 `onerror`、`decode()` 失敗需可再次請求；不要永久快取 null。顯示中性、固定尺寸的載入／缺圖替代框，保留文字與操作；成功後只更新仍在使用且符合當前事件的畫面，不能跳到過期場景或洩漏隱藏敵人。
- 音效缺少 BUF 時，提高該資源的未來載入優先度；當下優先使用已核准的同語意備援，不等待下載後補播。備援觸發與真實播放只能二擇一；保持原音量類別與既有 `sfx()` 回傳時間契約，不以網路等待時間當作聲音長度。
- 盤點現有 FALL、SYN、SCUE、特殊弓弩音效、無線電及持續聲，列出每個無備援項目。可用既有已核准且語意相符的備援；無相符音效時，維持安靜降級並明確記錄，提出候選給主人核准，不擅自拿不相干的聲音替代（例如遠處槍聲不可改成無關聲音）。不可宣稱所有音效都有備援，除非逐項驗證。
- 語音／無線電、音樂、雨聲、發電機等各有時效；短暫事件錯過即取消，仍在進行的循環音可在重新就緒後依目前情境恢復；切換場景、死亡、關閉音效或離開分頁後不可幽靈播放。
- 音檔前導靜音與下載延遲分開量測。此次不擅自裁剪原始音檔、改混音或改事件對應；將仍有主觀延遲的音檔另列後續決策。

### 3.7 演出同步（單人、多人）

- 單人：在演出時間軸啟動前預先確認該演出必要的圖片、音效與配樂播放狀態；預載在前一個安全時點完成。若還缺檔，僅允許在既有演出開始前做有上限的準備；達上限用已核准降級方式，之後按照原時間軸執行。不得讓資源延遲改變擲骰、傷害、事件順序或 QTE。
- 多人：各裝置獨立下載。不要等待所有客戶端就緒才讓房主開始，避免單台慢速或斷線手機阻塞整個房間。沿用既有共享演出時間軸、狀態同步及房主交接；慢速端依當前進度接上，過期短音效／特效不重播。已解碼必要立繪如稍晚就緒，只有畫面仍有效才替換中性框。
- 事件排程／延遲回呼需帶現有局、節點、戰鬥、演出或動作識別與取消條件；使用本機事件識別或既有同步識別，不新增遊戲規則或持久化跨局狀態。連續攻擊、快速切換、重送、倒序封包及房主交接都不得造成重複音效、重複演出、傷害重複或鎖死。
- 配樂使用原本的三軌與淡入淡出設定。追蹤 canplay／playing／waiting／stalled／error 及 play() 結果，適當重試或格式備援；過期的播放 Promise 不可反過來停止新曲。不可自行改變已定案的重拍對齊方式。

## 4. 開發階段與交付順序

### 5.1 建議量測指標

需輸出冷／暖快取的入口時間、P1 ready 時間、總下載位元組、各類資源快取命中率、重試數、真正播放／備援／過期取消／非預期漏播數、音效觸發到可量測輸出的時間、圖片就緒與演出顯示的差值、解碼記憶體估算與峰值、配樂卡頓次數。測試須區分音檔前導空白與載入延遲。

建議目標（工程驗收建議，非已驗證承諾）：正常且必要資源已就緒時，短音效從呼叫到排程不額外等待網路；量測可辨識瞬態時可用 100 ms 內作為初始參考（扣除既有刻意排程／音檔前導空白，實測再定）；暖快取未變素材無重複完整下載（正常版本檢查／媒體 Range 不算）；核心演出非預期漏播／缺圖為 0；故障注入中的合理降級與過期取消應另列而非當成成功播放。若受裝置政策或資源特性限制，附證據及例外理由，不自行放寬設計。

### 5.2 測試真實性

使用 Playwright 真實瀏覽器、可控網路限速／延遲／錯誤注入、真實波形分析、請求紀錄、畫面截圖。SW 快取測試要用可真正啟動 SW 的本機 HTTP(S) 環境及正式站驗收，不可只用路由模擬就聲稱 SW 已驗證。應包含正常自動播放政策，不能只用允許自動播放的測試模式。既有 QA 暫緩項目不得假裝已修正或通過。

結果只能是：通過／失敗／未測試（附原因）。原 QA 工具若有暫緩／略過，照實保留並解釋。Android 手機實機一律待主人實機驗收。若工作環境無法執行某種瀏覽器或正式 Firebase 情境，明確記錄未測試；必要驗收未完成不得直接宣稱全數通過或部署。
